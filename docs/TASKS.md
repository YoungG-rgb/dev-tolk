### [~] MVP-008. tolk-engine: декодирование аудио, команды `probe` и `extract`
- **Цель:** надёжно превращать аудио и аудиодорожки видео в моно 16 кГц f32 без FFmpeg и ручной установки зависимостей (TD-07, Q-09).
- **Результат:**
  - Cargo workspace с крейтом `engine`;
  - декодирование и ресемплинг (symphonia 0.6 + rubato 5) для MP3, M4A (AAC-LC, ALAC), WAV, FLAC, OGG Vorbis, **Opus** (OGG, WebM/MKV — `symphonia-adapter-libopus`) и **аудиодорожки из MP4/MOV** (первая дорожка с поддерживаемым кодеком, видеопоток не декодируется);
  - команда `tolk-engine probe <file>` выводит JSON: контейнер, кодек, длительность, частота, каналы, есть ли видео — или код ошибки;
  - команда `tolk-engine extract <video> <out.wav>` сохраняет аудиодорожку как WAV 16 кГц моно 16 бит, атомарно (TD-09, Q-15);
  - понятные коды ошибок: «кодек не поддерживается» (с названием кодека), «нет аудиодорожки», «файл повреждён», «нет доступа».
- **Критерии приёмки:**
  - все файлы корпуса A1–A6 декодируются;

  - прибавка к размеру бинарника от декодеров измерена и записана в TD-07.
- **Зависимости:** MVP-003
- **Приоритет / размер:** P0 / M

- **Прогресс (2026-10-18):** реализованы `probe`, `extract`, декодирование и ресемплинг (`crates/engine`), коды ошибок, протокол (`docs/ENGINE_PROTOCOL.md`). 15 автотестов проходят на macOS arm64 (`cargo test`, clippy без замечаний).

  - опциональные таймкоды `[чч:мм:сс]`;
  - шрифт задан явно для `ascii/hAnsi/cs`;
  - номера страниц в колонтитуле;
  - диалог сохранения;
  - имя файла по умолчанию из имени записи;
  - экспорт текущей (отредактированной) версии.
- **Критерии приёмки:**
  - документ из A1 открывается без предупреждений в Word (Windows и macOS), LibreOffice, Google Docs; в Pages — открывается, ограничения допустимы и фиксируются;
  - кириллица отображается одним шрифтом;
  - с таймкодами и без — оба варианта корректны.
- **Зависимости:** формат транскрипта из MVP-009; UI-кнопка — после MVP-020. Сам модуль можно делать параллельно с этапами 4–6.
- **Приоритет / размер:** P0 / M
- **Риски:** различия рендеринга полей номеров страниц в Pages.
- **Проверки:**
  - unit-тест: DOCX валиден (zip, document.xml), содержит ожидаемый текст;
  - ручная проверка в четырёх редакторах.

## Этап 8. Модели

### [ ] MVP-022. Каталог моделей, определение системы и рекомендация
- **Цель:** знать, какие модели доступны и какую рекомендовать этой машине (TD-13, TD-14).
- **Результат:**

- **Критерии приёмки:**
  - рекомендация совпадает с таблицей TD-14 для 8/16/24 ГБ (unit-тест);

- **Приоритет / размер:** P0 / S
- **Риски:** пороги будут уточнены на пилоте — каталог должен легко меняться в коде.

### [ ] MVP-023. Загрузка, проверка и установка модели; импорт из файла
- **Цель:** установить модель один раз, надёжно и только с согласия пользователя (TD-13).
- **Результат:**
  - диалог перед загрузкой: название, версия, размер, источник;
  - загрузка в `models/<file>.part`: докачка через Range, новый resolve-URL на каждую попытку, потоковая SHA-256, атомарный rename;
  - прогресс, скорость, отмена, кнопка «Повторить»;
  - проверка свободного места до начала;
  - установка VAD-модели вместе с основной;
  - понятные ошибки сети: нет соединения, домен недоступен, TLS-ошибка, HTTP 403/5xx, таймаут. В каждой — предложение импортировать модель из файла;
  - импорт модели из локального файла с проверкой SHA-256 по каталогу;
  - системный прокси используется, если настроен; корпоративный прокси не требуется.
- **Критерии приёмки:**
  - загрузка начинается только после подтверждения с показанными названием, версией, размером и источником;
  - обрыв сети → «Повторить» продолжает с места остановки;
  - подменённый или усечённый файл отклоняется и не устанавливается;
  - модели не скачиваются повторно и автоматически;
  - при заблокированной сети показывается понятная ошибка, а импорт из файла работает без сети.
- **Зависимости:** MVP-022, MVP-015
- **Приоритет / размер:** P0 / L
- **Риски:**
  - блокировка доменов `*.hf.co` в сети компании;
  - смена схемы CDN Hugging Face.
- **Проверки:**
  - тест обрыва (отключить сеть на середине);
  - тест с испорченным файлом;
  - тест с заблокированным в брандмауэре доменом.

### [ ] MVP-024. Управление моделями и первый запуск
- **Цель:** пользователь понимает, какая модель установлена и используется, и получает предупреждения о памяти.
- **Результат:**
  - экран «Модели»: установленные и доступные, размер, рекомендованная, выбор модели по умолчанию, удаление;

- **Критерии приёмки:**

## Этап 9. Словарь терминов

### [ ] MVP-036. Словарь терминов: хранение, редактирование, экспорт и импорт
- **Цель:** пользователь ведёт свой локальный список терминов и обменивается им с коллегами без сервера (TD-18, Q-12).

### [ ] MVP-037. Применение словаря при распознавании и измерение эффекта
- **Цель:** повысить точность терминов, не ухудшив общий текст, и честно измерить эффект (TD-18).
- **Результат:**
  - параметр движка `--glossary <file>` (активные термины);
  - для Whisper — подсказка `initial_prompt` с `carry_initial_prompt` и контролем длины в токенах; для GigaAM, если он выбран, — hotwords sherpa-onnx (если модель их поддерживает);
  - постобработка: замена только по явным вариантам пользователя (целое слово, без учёта регистра). Результат пишется в `transcript.json`, `original.json` не меняется;

  - отчёт замеров на A4 и A5 в `BENCHMARK_PLAN.md` в трёх режимах: без словаря / с подсказкой / с подсказкой и постобработкой.

- **Зависимости:** MVP-009, MVP-016, MVP-036, MVP-002 (тестовый словарь)

- **Риски:**

  - русские словоформы («Jira» → «джиру», «джирой») не покрываются заменой без морфологии. Это ограничение MVP, не гарантия.
- **Проверки:** замеры по BENCHMARK_PLAN §5.2 (метрика «точность терминов»); unit-тесты постобработки.

## Этап 13. Замеры на устройствах сотрудников, пилот и приёмка

### [ ] MVP-038. Замеры на устройствах сотрудников и фиксация системных требований
- **Цель:** подтвердить совместимость и зафиксировать системные требования только по измерениям (Q-14, TD-14).
- **Результат:**
  - в приложении для каждого задания локально сохраняются: длительность записи, время обработки, пиковая память движка, бэкенд (Metal/Vulkan/CPU), модель, результат (успех или код ошибки). Данные берутся из события `done` (MVP-009);
  - кнопка «Сохранить отчёт о производительности» создаёт файл. В файле:
    - есть: ОС, CPU, RAM, метрики заданий;
    - **нет:** текста транскриптов и имён файлов.
    
    Сотрудник передаёт файл вручную, сетевой отправки нет;
  - замеры на реальных устройствах сотрудников или временно доступных компьютерах, по каждой встреченной конфигурации (ОС × класс RAM × CPU/GPU):
    - время распознавания;
    - пиковая RAM;
    - стабильность — сбои за неделю работы;
    - качество — оценка пользователя 1–5 и выборочная проверка 5 минут текста;
  - `docs/SYSTEM_REQUIREMENTS.md`: таблица конфигураций со статусом «проверено / ограниченно / не проверено» и рекомендуемой моделью; итоговые пороги в TD-14.
- **Критерии приёмки:**
  - системные требования содержат только измеренные конфигурации; остальные явно помечены «не проверено», производительность для них не обещается;
  - для каждого класса RAM, который есть у сотрудников (8 / 16 / 24 ГБ), есть хотя бы одно измерение — или явная пометка, что устройств этого класса не нашлось;
  - отчёт о производительности не содержит текстов и имён файлов (проверка на образце).
- **Зависимости:** MVP-030, MVP-031, MVP-025
- **Приоритет / размер:** P0 / M
- **Риски:** у сотрудников может не оказаться части конфигураций; замеры на рабочих машинах шумные из-за фоновых программ. Фиксировать условия и не делать выводов по одному прогону.
- **Проверки:** сверка метрик приложения с внешним замером (`/usr/bin/time -l`, Process Explorer) на H2 и одной Windows-машине: расхождение ≤ 10%.
